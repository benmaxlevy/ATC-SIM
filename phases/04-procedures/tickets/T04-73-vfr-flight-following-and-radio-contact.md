# T04-73 VFR flight following and radio-contact lifecycle

**Phase:** 04 Procedures (satellite traffic addendum)
**Priority:** P0
**Size:** L
**Depends on:** T04-72
**Blocks:** T04-74
**Launch:** Implement this ticket only. Do not start downstream tickets.

## Goal

Ambient airborne VFR traffic can make a structured flight-following request and
the controller can work the request through standby/details, beacon assignment,
IDENT, radar identification, approval/decline, and radar-service termination.
The same request record is extensible to the airborne IFR-pickup request used by
T04-74. Flight-following state is independent of flight rules, the editable
flight plan, active IFR clearance, scope ownership, and kinematics.

## Context

T04-72 schedules the VFR calls and owns the request percentage/cap. This ticket
owns the request state machine and the controller-facing radio commands. Existing
`SQ`, `I`, and `MVFR` behavior remains available. `SQ` changes the aircraft's
surveillance transponder state only; it never edits a flight-plan beacon.

The current radio pipeline is controller command line/PTT → parser → pilot
agent → readback. New controller instructions must use the same browser and
self-hosted Path C schema/grammar/validator/eval path. Pilot calls are structured
traffic events from the scheduler, not unconstrained text generated by an LLM.

## Research

- **R01:** FAA JO 7110.65, §5-1-8, Position Reporting:
  https://www.faa.gov/air_traffic/publications/atpubs/atc_html/chap5_section_1.html
  Official position wording includes `(number of miles) MILES FROM (fix)`.
- **R01:** FAA JO 7110.65, §5-3-1 and §5-3-3, Radar Identification:
  https://www.faa.gov/air_traffic/publications/atpubs/atc_html/chap5_section_3.html
  Radar service requires radar identification; `IDENT` is an identification aid,
  not a clearance.
- **R01:** FAA JO 7110.65, §7-9-2, VFR aircraft in Class B:
  https://www.faa.gov/air_traffic/publications/atpubs/atc_html/chap7_section_9.html
  Flight following does not itself authorize Class B entry. The generated
  Atlanta traffic remains outside Bravo; a later ticket may model a Bravo entry
  clearance.
- **R02:** FAA Pilot/Controller Glossary, `radar contact` and `flight
  following`: https://www.faa.gov/air_traffic/publications/atpubs/pcg_html/
- **R03:** FAA AIM radio communications / VFR traffic services:
  https://www.faa.gov/air_traffic/publications/atpubs/aim_html/

Trainer delta: this simulator has one local controller position and no live
coordination; “approved” means the local simulated service is active. The radar
contact position suffix is a logged informational report and is not proof of, or
an instruction to change, the aircraft's physical position.

## Scope

- Define a generic request record with `kind` (`FLIGHT_FOLLOWING` or
  `IFR_PICKUP`), stable id, aircraft id, requested-at sim time, structured
  details, and lifecycle status:
  `PENDING -> AWAITING_DETAILS | STANDBY | IDENTIFYING -> IDENTIFIED ->
  APPROVED`, with terminal `DECLINED`, `WITHDRAWN`, and `TERMINATED` states.
  T04-74 supplies the `IFR_PICKUP` consumer; do not duplicate this state type.
- Keep request/service data separate from `Aircraft.flightRules`,
  `flightPlan`/`fp`, `FlightPlan`, `activeClearance`, `intent`, radar ownership,
  and CA/MSAW calculations. Add an explicit effective operational-service view
  for scope/list consumers rather than rewriting a manual plan.
- Emit deterministic pilot request/detail events from scheduler-owned data;
  retries after `SAY REQUEST` do not consume the new-request-per-hour cap.
- Add controller instructions to Command IR and all parser paths:

  | Full controller form | IR | Existing/allowed shorthand |
  | --- | --- | --- |
  | `say request` | `REQUEST_DETAILS` | none |
  | `stand by` | `STANDBY_REQUEST` | none |
  | `approve flight following` | `APPROVE_FLIGHT_FOLLOWING` | none |
  | `unable flight following` or `unable to provide flight following` | `DECLINE_REQUEST { service: "FLIGHT_FOLLOWING" }` | none |
  | `radar contact <distance> miles from <catalog fix/navaid>` | `RADAR_CONTACT { distanceNm, referenceId, referenceKind }` | none |
  | `radar service terminated` | `TERMINATE_RADAR_SERVICE` | none |

  `SQ <code>`, `SQ VFR`, `I`, and spoken `squawk ...` / `squawk ident` retain
  their existing shapes and aliases. Do not add new compact abbreviations.
- `RADAR_CONTACT` accepts a positive finite distance in NM (numeric or spoken
  number) and an exact/alias-grounded catalog fix or navaid. Store the suffix and
  timestamp for the request log/strip; never move, vector, reroute, or snap the
  aircraft to that reference.
- Gate service actions to the request state. `SQ` and `I` may be issued while a
  request is open; IDENT records an identification attempt and starts the normal
  flash. `RADAR_CONTACT` confirms identification. Approval requires an open
  flight-following request in `IDENTIFIED`; decline requires an open request;
  termination requires active radar service. A request-control instruction is
  one instruction per transmission; `SQ`/`I` remain separate transmissions.
- Add readbacks and exact reject readbacks. Existing `SQ` and `I` readbacks stay
  unchanged.
- Add tests for generic synthetic fixtures, including request cap/retry behavior,
  no-request and duplicate handling, browser/Path C parity, and scope/list
  projections. CA/MSAW must continue to evaluate all eligible tracks without a
  new rules-based separation algorithm.

## Out of scope

- Airborne IFR-clearance execution, IFR cancellation, or destination eligibility
  (T04-74/T04-75).
- Ground requests, Bravo entry clearances, live multi-position coordination,
  tower cab behavior, or a cloud speech provider.
- Automatic VFR squawk on service termination; only an explicit `SQ VFR` does so.
- Geometry validation of the radar-contact suffix, route changes, vectors, or
  simulated separation changes from the informational position phrase.

## Implementation notes

Suggested IR additions (names are contract, not a license to add aliases):

```ts
| { type: "REQUEST_DETAILS" }
| { type: "STANDBY_REQUEST" }
| { type: "APPROVE_FLIGHT_FOLLOWING" }
| { type: "DECLINE_REQUEST"; service: "FLIGHT_FOLLOWING" | "IFR_PICKUP" }
| { type: "RADAR_CONTACT"; distanceNm: number; referenceId: string; referenceKind: "FIX" | "NAVAID" }
| { type: "TERMINATE_RADAR_SERVICE" }
```

Use the shared catalog matcher for the fix/navaid slot. A tied/unknown reference
is a parse miss; Path C may select only a unique supplied catalog candidate whose
transcript span supports the reference. Path C must not infer the distance,
reference, request kind, or service action from unrelated text.

State effects are atomic: reject before changing status, IDENT flash, squawk,
service, plan, route, ownership, or kinematics. `APPROVE_FLIGHT_FOLLOWING`
activates only the VFR advisory-service marker; it does not change operational
flight rules or authorize Class B. `TERMINATE_RADAR_SERVICE` clears only the
service marker and closes the associated request; it does not clear an IFR
clearance or force VFR squawk.

Exact lifecycle error details (the readback may preserve existing concise
templates) are:

| Condition | Reason/detail |
| --- | --- |
| no open request for request action | `REQUEST: no pending radio request` |
| duplicate request from same aircraft/service | `REQUEST: request already pending` |
| standby/details after request is terminal/approved | `REQUEST: request is already resolved` |
| approval before radar contact | `REQUEST: radar identification required` |
| decline after approval | `REQUEST: active service must be terminated` |
| termination without active service | `REQUEST: radar service is not active` |
| unknown or non-positive position suffix | `UNKNOWN_FIX` / `RADAR_CONTACT: distance must be positive` |

Controller readbacks are deterministic: `say request`, `standby`, `flight
following approved`, `unable flight following`, `radar contact, <N> miles from
<reference>`, and `radar service terminated`, prefixed by callsign once.

Update the local Help modal, `docs/USER.md`, `phases/04-procedures/README.md`,
`phases/_shared/command-ir.md`, and `phases/_shared/parse-pipeline.md` with
these exact forms, precedence, and trainer limits. Update
`speech-api/parse_engine.py`, `speech-api/parse_grammar.gbnf`, mock/contract
tests, and the live eval corpus in the same coherent change.

## Acceptance criteria

- [ ] **AC1 — Request state:** Scheduler requests are stable, deduplicated,
  cap-aware, retry-safe, and expose the lifecycle above.
- [ ] **AC2 — Full command grammar:** All six new full forms parse with exact
  field order; incomplete, malformed, ambiguous, duplicate, and modifier-conflict
  inputs reject without side effects. Existing `SQ`, `I`, `MVFR`, and `CAPP`
  behavior remains unchanged.
- [ ] **AC3 — Service transaction:** Squawk/IDENT, identification,
  approve/decline, and termination have the exact gates and independent effects.
- [ ] **AC4 — Radar contact:** Distance/reference is catalog-grounded and
  logged as information only; no position or navigation mutation occurs.
- [ ] **AC5 — Consumers:** Datablock/VFR list/request presentation uses the
  operational service state; CA/MSAW continue to consume tracks without a new
  separation rule.

  `speech-api` instruction set/prompt/GBNF/validator/mock/evals, and Path C guard
  agree; no cloud fallback is introduced.
- [ ] **AC7 — Help/docs:** Help modal, `docs/USER.md`, phase README, and shared
  command/parse contracts document the forms, errors, readbacks, and trainer
  deltas.
